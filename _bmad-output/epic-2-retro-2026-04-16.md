## Successes

1. **Shared ingestion pipeline architecture** — the fingerprint gate (1-11), `batchUpsertCandidatesFromATS` (2-3), `process_import_chunk` RPC (2-1), sync-run tracking (2-4b), and scheduler (2-7) created a reusable foundation. Each new connector (PDF 2-2a, Clay 2-8) plugged in with zero cross-cutting plumbing. Velocity increased with each connector because the infrastructure already existed.

2. **Story 2-8 Clay webhook** — the highlight of the epic per Vivek. Demonstrated adaptive delivery at its best: correct-course workflow to add the story, pull-to-push pivot after real-payload discovery, webhook.site capture as a design tool, 79 tests with production regression fixture, adversarial 3-layer code review (35 findings → 13 patches applied inline), production-verified same day with Kristen Price as the first real candidate. The hourly-bucket observability fix was driven by real user feedback in the same session.

3. **Cross-cutting instrumentation shipped late and safely** — Story 2-4b's `createSyncRun()` was retrofitted into 5 existing jobs post-deployment with null-safe no-throw semantics. Established the principle that observability can ship after the core feature without risk.

4. **Fingerprint backfill at scale** — Story 2-5's server-side SQL INSERT of 731K fingerprints enabled dedup to work against the full candidate corpus on day one. No client-side iteration, no batch jobs.

5. **Review quality improved over the epic** — adversarial dual-model reviews went from 0 in the first half to 6/7 in the second half. Story 2-8's structured 3-layer review (Blind Hunter + Edge Case Hunter + Acceptance Auditor) set the new bar.

## Challenges

1. **Stories 2-4 and 2-5 were the most frustrating** (per Vivek). Both were foundational data-model-defining stories where getting the schema wrong meant rework for every downstream story. Story 2-4 (candidate search) was reworked twice (PostgREST → SQL RPC). Story 2-5 (dedup) required careful identity-confidence threshold tuning. Neither got an adversarial review before downstream stories started depending on them.

2. **Stubs shipped as "done" in early stories** — Stories 2-1, 2-3, and 2-5 had CRITICAL review findings where core persistence or scheduling was stubbed out but marked as complete. This pattern disappeared in the second half of the epic as review rigor increased, but it burned time in the early stories.

3. **External-system payload shape surprises** — Ceipal's auth field was `email` not `username` (Story 2-3). Clay's nested LinkedIn blob lives under `enrichlinkedin_data` not `Enrich person` (Story 2-8). Vendor docs never match reality. Each new connector burned discovery cycles that could have been front-loaded with a webhook.site capture.

4. **Grant/permission over-breadth** — `anon` role getting INSERT/UPDATE/DELETE access was caught in review in 3 separate stories (2-1, 2-3, 2-4b). Systemic issue: the schema migration template defaults to broad grants.

5. **Migration DELETE wiped observability data** — Story 2-8's hourly-bucket migration included an unconditional `DELETE FROM sync_runs WHERE source='clay_enrichment'` meant to clean up 30 test rows, but a real backfill of 5,953 rows had already run. Lesson learned: never put destructive DELETEs on audit/observability tables in reusable migrations.

## Key Decisions Made During Retro

1. **Scope growth is a feature, not a bug.** Vivek's working style is to discover requirements by building. Instead of fighting the 86% growth, plan for it: assume every epic will roughly double and build buffer accordingly.

2. **"Discover before you code" rule for external integrations.** Every new third-party connector story starts with a payload-discovery spike (webhook.site, curl capture, or API explorer) before any code is written. The captured JSON becomes the frozen test fixture.

3. **Adversarial review foundational stories first.** Data-model-defining stories get the dual-model review before downstream stories start depending on them — prevents the 2-4/2-5 rework pattern.
